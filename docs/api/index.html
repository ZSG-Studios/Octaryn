Octaryn API

Current shared API surface.

The public module API lives in octaryn-shared/Source. Game modules implement registration and gameplay through shared contracts; client and server owners keep rendering, persistence, transport, and native bridges private.

Module Entry Point

A game module exposes IGameModuleRegistration. The host reads the manifest, validates it, then calls CreateInstance with a narrow ModuleHostContext.

public interface IGameModuleRegistration
{
    GameModuleManifest Manifest { get; }

    IGameModuleInstance CreateInstance(ModuleHostContext context);
}

public interface IGameModuleInstance : IDisposable
{
    void Tick(in ModuleFrameContext frame);
}

Basegame also implements provider interfaces when it supplies server authority or world-generation rules.

Manifest Contract

GameModuleManifest is the deny-by-default declaration for a module. Every capability, host API, package, content file, asset file, and scheduled system must be declared here.

public sealed record GameModuleManifest(
    string ModuleId,
    string DisplayName,
    string Version,
    string OctarynApiVersion,
    IReadOnlyList<string> RequiredCapabilities,
    IReadOnlyList<string> RequestedHostApis,
    IReadOnlyList<string> RequestedRuntimePackages,
    IReadOnlyList<string> RequestedBuildPackages,
    IReadOnlyList<string> RequestedFrameworkApiGroups,
    IReadOnlyList<GameModuleDependency> ModuleDependencies,
    IReadOnlyList<GameModuleContentDeclaration> ContentDeclarations,
    IReadOnlyList<GameModuleAssetDeclaration> AssetDeclarations,
    GameModuleScheduleDeclaration Schedule,
    GameModuleCompatibility Compatibility);
DeclarationCurrent Rule
GameModuleContentDeclarationContent IDs are module-owned and paths must live under Data/.
GameModuleAssetDeclarationAsset IDs are module-owned and paths must live under Assets/ or Shaders/.
GameModuleDependencyDependencies declare module ID plus min/max version range.
GameModuleCompatibilityDeclares host API range, save compatibility ID, and multiplayer support.

Capabilities describe what a module is allowed to do. Host APIs describe which host surfaces it can request. Requesting an ID is not enough; the schedule must also declare the matching resource access.

Packages And Framework API Groups

Module package access is allowlisted. Version pins in Directory.Packages.props do not grant permission by themselves.

Allowed Runtime PackagePurpose
ArchManaged ECS for gameplay/module logic.
Arch.SystemArch system support.
Arch.EventBusGameplay event bus support.
Arch.RelationshipsGameplay relationship support.

Arch.System.SourceGenerator is currently the only allowed build/analyzer package. Allowed framework groups are BCL primitives, collections, memory, math, time, and text. Filesystem, networking, process, reflection, runtime code generation, native interop, threading, environment, console, and unsafe code groups are denied for modules.

Runtime Context

ModuleHostContext is intentionally narrow. It currently exposes module command requests only.

public readonly record struct ModuleHostContext(
    IModuleCommandRequests Commands);

public readonly record struct ModuleFrameContext
{
    public double DeltaSeconds { get; }
    public ulong FrameIndex { get; }
    public WorldTime WorldTime { get; }
}

WorldTime includes tick ID, day index, delta seconds, and total world seconds. Calendar display data uses WorldTimeSnapshot.

Command Requests

Modules request commands; the server owner validates and applies authoritative edits. Block edits must request world.block_edits, request host.commands, and declare host.commands as a scheduled write.

public interface IModuleCommandRequests
{
    bool TryRequest(ModuleCommandRequest request);
}

public enum ModuleCommandRequestKind : uint
{
    None = 0,
    SetBlock = 1
}

public readonly record struct ModuleCommandRequest(
    ModuleCommandRequestKind Kind,
    ulong RequestId,
    BlockEdit BlockEdit)
{
    public static ModuleCommandRequest SetBlock(BlockEdit edit, ulong requestId = 0);
    public static ModuleCommandRequest BreakBlock(BlockPosition position, ulong requestId = 0);
}

Authority And Worldgen Providers

Game modules can provide gameplay rules through explicit provider interfaces. The server still owns authority, persistence, and validation.

public interface IBlockAuthorityRulesProvider
{
    IBlockAuthorityRules BlockAuthorityRules { get; }
}

public interface IBlockAuthorityRules
{
    bool IsKnownBlock(BlockId block);
    bool CanApplyEdit(BlockEdit edit, BlockId belowBlock);
    bool CanStaySupported(BlockId block, BlockPosition position, BlockId belowBlock);
    bool IsClientPlaceable(BlockId block);
    bool IsSolidBlock(BlockId block);
}

public interface IWorldGenerationRulesProvider
{
    IWorldGenerationRules WorldGenerationRules { get; }
}

IWorldGenerationRules provides water height, water block, material rules, terrain column planning, and feature block emission. Generated seed terrain must remain memory/VRAM only; authoritative edits are the persisted data.

Validation Rules

GameModuleValidator.Validate checks manifest shape before activation.

  • Required text, versions, compatibility range, and save compatibility ID.
  • Unique capabilities, host APIs, packages, content IDs, asset IDs, paths, and scheduled systems.
  • Module-owned declaration IDs for content, assets, and systems.
  • Content kinds: block, item, material, recipe, tag, loot_table, feature, biome, rule.
  • Asset kinds: atlas, blockstate, model, shader, texture, ui, audio.
  • Safe relative paths only, with content under Data/ and assets under Assets/ or Shaders/.
  • Host API and package allowlists plus denied framework API groups.
  • Schedule graph, resource overlap, and command-write capability requirements.

Owner Boundary

Modules should depend on octaryn-shared and approved packages only. They do not receive raw rendering, GPU upload, transport sessions, server persistence, filesystem, native pointers, raw threads, process control, or broad service locators. Use Examples for a concrete module skeleton.
