For your engine, I’d build the DDGI system around one rule:

> **Every useful voxel position can permanently own a probe, but only probes that currently matter consume GPU work.**

Your `32×32×32` chunks are a very good unit for this. The world can be 32 chunks tall or much larger horizontally without tying GI updates to the whole world.

## 1. Overall architecture

```text
                         VOXEL WORLD
                      32 × 32 × 32 chunks
                              │
             ┌────────────────┼─────────────────┐
             │                │                 │
             ▼                ▼                 ▼
       Greedy Mesher      Voxel Data       Light System
             │                │                 │
             ▼                │                 │
        Chunk BLAS            │                 │
             │                │                 │
             └────────────┐   │   ┌─────────────┘
                          ▼   ▼   ▼
                         EVENT BUS
                             │
                 ┌───────────┴────────────┐
                 ▼                        ▼

                 │                        │

                       PROBE SCHEDULER
```

Your RT shadows, reflections and DDGI should all consume the **same current-world TLAS**.

# 2. One potential probe per voxel

With 1-block spacing:

```text
Voxel coordinates:
(100, 220, 40)

Probe:
(100.5, 220.5, 40.5)
```

You don't need to explicitly store the position.

```cpp
float3 GetProbePosition(int3 voxel)
{
    return float3(voxel) + 0.5f;
}
```

That saves memory immediately.

A `32³` chunk therefore has:

**32,768 potential probe positions.**

But that does **not** mean 32,768 probes trace rays.

Most might look like:

```text
Solid       → Disabled
Useful air  → Awake/Sleeping
Sky/open    → Sleeping
```

# 3. Probe state machine

This is the heart of the system.

I would use something approximately like:

```cpp
enum ProbeState : uint8_t
{
    PROBE_SOLID,        // voxel occupied; no GI work
    PROBE_DORMANT,      // valid probe, 0 work
    PROBE_WAKE,         // needs validation
    PROBE_DIRTY,        // geometry/light changed
    PROBE_CONVERGING,   // receiving aggressive updates
    PROBE_ACTIVE        // normal periodic updates
};
```

So:

```text
                        BLOCK/LIGHT EVENT
                               │
                               ▼
 DORMANT ────────────────► WAKE/DIRTY
   ▲                           │
   │                           ▼
   │                      CONVERGING
   │                           │
   │                           ▼
   └─────────────────────── ACTIVE
                               │
                         low variability
                               │
                               ▼
                            DORMANT
```

**Dormant does not mean deleted.**

The probe remains there.

Its:

* irradiance
* distance
* validity
* previous lighting
* position/state
* timestamps

remain intact.

It simply costs:

**0 rays + 0 blend work + 0 relocation work** until something wakes it.

This follows the same general optimization principle as RTXGI probe classification, which marks useless probes inactive specifically to avoid tracing and blending work. ([GitHub][1])

# 4. Separate probe existence from probe activity

This is important.

I'd use three concepts:

```text
Exists
Useful
Needs work
```

Example:

```text
Air probe in a cave:

exists      = true
useful      = true
needsWork   = false
```

That's your dormant probe.

Another:

```text
Probe inside stone:

exists      = true
useful      = false
needsWork   = false
```

You haven't deleted it.

If that block gets mined:

```text
useful      = true
needsWork   = true
```

Then it wakes.

# 5. Your one-ray idea

I WOULD keep it, but use it as a **wake/classification fast path**, not as your only correctness mechanism.

For a sleeping probe:

```text
0 rays/frame
```

When an event potentially affects it:

```text
1 cheap test ray
```

If that ray indicates something meaningful has changed:

```text
full refresh
```

Otherwise:

```text
back to sleep
```

So:

```text
Dormant Probe
      │
      │ nearby edit/light event
      ▼
  WAKE CHECK
      │
    1 ray
      │
 ┌────┴────┐
 │         │
changed   nothing
 │         │
 ▼         ▼
DIRTY    DORMANT
```

That's a good optimization.

But because yours is a voxel world, use the **voxel occupancy information first**.

For example:

```cpp
if (VoxelChangedNearProbe(probe))
{
    probe.state = PROBE_DIRTY;
}
else
{
    RunWakeRay(probe);
}
```

You don't need a ray to discover that a block 1 meter away was placed—you already know it happened.

The ray becomes useful for determining whether the resulting change actually matters to that probe.

# 7. Use revisions instead of constantly touching everything

AAA-scale trick:

Have:

```cpp
uint WorldGeometryRevision;
uint LightingRevision;
```

And regional revisions:

```cpp
struct ChunkGIState
{
    uint geometryRevision;
    uint lightingRevision;
};
```

Probe stores:

```cpp
probe.geometryRevisionSeen;
probe.lightRevisionSeen;
```

Then:

```cpp
if (probe.geometryRevisionSeen != region.geometryRevision)
    geometryDirty = true;

if (probe.lightRevisionSeen != region.lightRevision)
    lightingDirty = true;
```

That avoids CPU loops resetting thousands of flags.

# 8. Block destruction pipeline

Suppose the player mines one block.

```text
Block destroyed
      ↓
Voxel data changed
      ↓
chunk generation++
      ↓
greedy remesh
      ↓
chunk BLAS rebuild
      ↓
TLAS update
      ↓
GI dirty AABB generated
      ↓
wake probes intersecting AABB
      ↓
classification
      ↓
aggressive DDGI convergence
```

### Geometry side

Because greedy meshing changes triangle topology, don't assume a BLAS refit is always legal.

Vulkan AS update operations restrict what can change; arbitrary primitive/topology changes aren't equivalent to simply moving existing vertices. For your greedy remesh, a **chunk BLAS rebuild** is therefore the safe general path. ([Vulkan Documentation][2])

So:

```cpp
VoxelChanged(chunk)
{
    RebuildGreedyMesh(chunk);
    RebuildBLAS(chunk);
    UpdateTLASInstance(chunk);
}
```

Your `32³` chunks are a reasonable BLAS unit.

```cpp
if(local.x == 0)  DirtyChunk(chunk + int3(-1,0,0));
```

# 10. Dirty GI regions

Every geometry event creates:

```cpp
struct GIDirtyRegion
{
    AABB bounds;

    uint reason;

    float importance;
};
```

Reasons:

```cpp
GEOMETRY_ADDED
GEOMETRY_REMOVED
MATERIAL_CHANGED
EMISSIVE_CHANGED
LIGHT_ADDED
LIGHT_REMOVED
LIGHT_MOVED
```

Different events trigger different work.

| Event                   | Irradiance | Visibility/distance | Classification |
| ----------------------- | ---------: | ------------------: | -------------: |
| Block placed            |        Yes |                 Yes |            Yes |
| Block removed           |        Yes |                 Yes |            Yes |
| Texture changed         |      Maybe |                  No |             No |
| Material albedo changed |        Yes |                  No |             No |
| Emissive changed        |        Yes |                  No |             No |
| Torch placed            |        Yes |                  No |     Maybe wake |
| Torch removed           |        Yes |                  No |             No |
| Sun changed             |        Yes |                  No |             No |

That prevents unnecessary passes.

Don't automatically dirty a massive sphere.

Start tight:

```text
        1-block edit

          X

       immediate
      dirty probes

      P P P
      P X P
      P P P
```

Then allow lighting change to propagate through probe variability.

I would have three rings:

```text
Ring 0
0–2 probes
IMMEDIATE

Ring 1
2–6 probes
HIGH PRIORITY

Ring 2
6–16 probes
LOW PRIORITY
```

Example:

```cpp

else if(distance < R1)

    priority = BACKGROUND;
```

# 12. Probe scheduler

This is what turns this into a serious renderer.

Do **not** simply loop over probes.

Build a GPU work queue.

```cpp
struct ProbeWorkItem
{
    uint probeIndex;
    uint priority;
    uint reason;
    uint rayBudget;
};
```

Priority score:

```cpp
priority =
      geometryDirty      * 10000
    + newlyActivated     * 9000
    + lightDirty         * 7000
    + nearCamera         * 3000
    + highVariability    * 2000
    + oldUpdate          * 1000;
```

Then GPU compaction/sort/buckets:

```text
CRITICAL
HIGH
NORMAL
BACKGROUND
```

You don't need a perfect sort.

Four buckets are plenty.

Do not give every probe the same number of rays.

RTXGI's reference configuration exposes `probeNumRays` and defaults to 256 rays/probe, but that's a tuning parameter rather than something your custom renderer must copy. ([GitHub][3])

I'd do something closer to:

### Brand-new / major geometry change

```text
128–256 rays
```

### Converging

```text
64–128 rays
```

### Normal active

```text
16–64 rays
```

### Stable

```text
4–16 occasionally
```

### Dormant

```text
0
```

### Wake test

```text
1
```

Now you're spending rays where humans actually notice the difference.


# 17. Probe relocation

For your one-probe-per-voxel design, normal relocation should be **small**.

You're already intentionally placing probes at voxel centers.

I'd allow perhaps:

```text
±0.35–0.45 block
```

inside their own voxel.

Never let:

```text
Probe A migrate into Probe B's logical voxel.
```

RTXGI similarly constrains relocation within the probe's grid cell, with the reference implementation limiting displacement relative to cell spacing. ([GitHub][1])

So:

```text
logical coordinate never changes

Voxel (22,44,19)
    │
    └── relocationOffset float3
```

Perfect.

# 19. Don't waste fixed classification rays constantly

RTXGI's reference classification uses fixed rays and defaults to 32 fixed rays so classification and relocation remain temporally stable. ([GitHub][1])

I would **not** blindly do 32 fixed rays for every probe every frame in your engine.

Your system knows when geometry changed.

So:

```text
normal frame:
NO reclassification

block edit:
only nearby probes classify

chunk load:
classify new probes

dynamic mesh passes through:
classify affected probes
```

That's one of the biggest advantages of building DDGI specifically for voxels rather than copying generic RTXGI behavior.

# 20. The one-ray dormant check

For your exact idea:

```slang
if(probe.state == PROBE_WAKE)
{
    WakeResult result = TraceWakeRay(probe);

    if(result.requiresRefresh)
        probe.state = PROBE_DIRTY;
    else
        probe.state = PROBE_DORMANT;
}
```

Change the wake-ray direction over events:

```cpp
directionIndex =
    Hash(probeIndex, regionRevision) % directionCount;
```

So if a probe gets woken multiple times, you're not always checking +X.

You could use a stable Fibonacci direction table.

# 22. Sunlight is different

Don't wake your whole world every time the sun moves 0.1°.

Quantize sunlight GI updates.

For example:

```text
direct sunlight:
every frame through RT shadows

indirect sun/DDGI:
update when sun moves N degrees
or
budget continuously
```

That way your RT shadowing remains perfectly dynamic while bounced sunlight updates more slowly.

Players generally tolerate that far better than you might expect because direct lighting provides the strongest motion cue.

# 28. One-probe-per-block makes probe texture resolution negotiable

Because your spatial probe density is extremely high, each individual probe may not need the same angular texture resolution as a conventional probe grid spaced 3–5 meters apart.

That is worth experimenting with.

Instead of immediately assuming:

```text
8×8 irradiance
16×16 distance
```

try:

```text
4×4 / 6×6 irradiance
8×8 distance
```

and measure.

Dense spatial samples can compensate for somewhat lower angular resolution.

That could be the difference between this architecture being merely cool and actually affordable.

# 29. Sampling at surfaces

At shading time:

```text
surface position
      ↓
find surrounding voxel cell
      ↓
8 neighboring probes
      ↓
discard invalid/solid probes
      ↓
visibility weighting
      ↓
trilinear weighting
      ↓
normal weighting
      ↓
irradiance
```

Basically:

```slang
float3 indirect = 0;
float weightSum = 0;

for(int i = 0; i < 8; ++i)
{
    Probe p = GetNeighborProbe(i);

    if(!p.useful)
        continue;

    float w =
        TrilinearWeight(p) *
        VisibilityWeight(p) *
        NormalWeight(p);

    indirect += SampleIrradiance(p) * w;
    weightSum += w;
}

indirect /= max(weightSum, 1e-5);
```

RTXGI similarly uses neighboring probes plus stored distance statistics to weight probe contributions and suppress occluded lighting. ([GitHub][5])

# 36. Probe convergence

Track something like:

```cpp
float variability;
```

Each update:

```cpp
variability =
    abs(newIrradiance - oldIrradiance);
```

EMA it.

Then:

```text
> 0.20
critical

0.05–0.20
converging

0.01–0.05
stable

< 0.01 for several updates
sleep
```

RTXGI includes probe variability specifically as a convergence metric. ([GitHub][1])

That's exactly the concept you want for deciding when to stop spending rays.


not necessarily:

```text
GEOMETRY_DIRTY
```

unless occupancy changed too.

---

# 48. Multiple bounce approximation

DDGI normally gives you temporal feedback possibilities.

But don't immediately feed 100% of old probe GI back into rays or you'll create energy explosions.

Have:

```text
primary bounce
+
controlled previous-frame indirect contribution
```

and clamp energy.

Get one-bounce rock solid before adding multi-bounce feedback.

---

# 49. Fire / rapidly changing lights

Don't wake/re-sleep every probe every flicker.

Separate:

```text
GI light intensity
```

from:

```text
visual light intensity
```

A fire might flicker visually at 20 Hz while GI injection changes smoothly at 3–5 Hz.

Far more stable.

---

Heatmap.


# 51. Capture per-event telemetry

You want to know:

```text
player broke 1 block

Chunks remeshed:      1
BLAS rebuilt:         1
Probes woken:        37
Probes refreshed:    21
Rays emitted:      2688
```

Then test:

```text

```

```text
500 × everything
```

Dirty AABBs should merge.

# 52. Event merging

Very important.

Explosion changes 500 voxels.

Don't enqueue 500 independent GI events.

Merge adjacent edits:

```text
block edits
   ↓
chunk-local changed bounds
   ↓
AABB union
   ↓
ONE GI dirty region
```

Potentially one region per affected chunk.

---

# 53. Triple-buffer event/work buffers

I'd use GPU-friendly ring buffers:

```text
Frame N
events

Frame N+1
consume

Frame N+2
safe reuse
```

Avoid stalls from reading CPU-written queues still in GPU use.

# 55. Prefer a common material evaluation path

Your reflection rays and DDGI rays should share:

```slang
EvaluateMaterial(...)
```

Otherwise eventually:

```text
raster material ≠ RT material ≠ GI material
```

and debugging becomes miserable.

---

# 56. Ray Query vs ray-generation pipeline

For a custom renderer I'd prototype DDGI using whichever path already powers your RT system.

Slang supports ray-tracing and ray-query capabilities, including SPIR-V ray query/ray tracing targets. ([GitHub][6])

Long term, ray queries from compute can be attractive for a scheduler-driven DDGI pass because your work naturally looks like:

```text
compute work item
→ trace
→ integrate
```

But profile both on AMD/NVIDIA.

Don't architect yourself into a vendor assumption.

---

# 57. NVIDIA-specific optimizations come later

SER / execution reordering can potentially help divergent RT workloads on hardware that supports it, and modern Slang exposes relevant ray tracing/reordering functionality. ([GitHub][7])

But:

**Do not make SER required.**

Your baseline must run correctly without it.

Then:

```text
NVIDIA path → optional SER
AMD path    → normal path
```

---

# 58. Cross-platform RHI layer

One warning specific to your stack:

Slang RHI's own repository currently describes the project as under active refactoring/development and says it is not yet ready for general use. ([GitHub][8])

For an engine you're trying to take to AAA-level robustness, I'd therefore have:

```text
Your Renderer API
       ↓
Your RT abstraction
       ↓
Slang RHI
       ↓
Vulkan / D3D12
```

Not:

```text
game systems
→ direct dependency everywhere on slang-rhi types
```

And pin a known-good Slang/Slang-RHI revision.

Don't update your compiler/RHI every week in production.

# The final design

This is what I'd ultimately aim for:

```text
              32×32×32 VOXEL CHUNKS
                       │
           ┌───────────┴───────────┐
           ▼                       ▼
     GREEDY MESH               VOXEL DATA
           │                       │
           ▼                       │
      CHUNK BLAS                   │
           │                       │
           └────────► TLAS ◄───────┘
                       │
                       │
              ┌────────┴────────┐
              │                 │
              ▼                 ▼
        RT SHADOWS        RT REFLECTIONS
              │                 │
              └────────┬────────┘
                       │
                       ▼
              VOXEL-DDGI SYSTEM
                       │
            1 logical probe/voxel
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
      SOLID         DORMANT        ACTIVE
     0 rays          0 rays           │
                        ▲             │
                        │             ▼
                        │           DIRTY
                        │             │
                        │       adaptive rays
                        │             │
                        │         convergence
                        │             │
                        └─────────────┘
                       │
                       ▼
        IRRADIANCE + DISTANCE HISTORY
                       │
                       ▼
              FINAL INDIRECT LIGHT
```

**That is the architecture I'd bet on for your engine.**

The big difference from ordinary DDGI is that your voxel engine knows exactly **when and where the world changes**, so you don't need to keep asking millions of probes whether they're still valid. Let them converge, put them to sleep, and wake only the probes touched by geometry/light events. That is what can make your one-probe-per-voxel idea practical at AAA scale.
